## Findings considered and rejected

These were raised during the audit, checked against the code, and found not to
be defects. Recorded so they are not re-audited.

- **`churches.controller.ts` `update`/`delete` accept a raw `:id` with no
  ownership check** — rejected. `ChurchContextGuard` is registered globally
  (`app.module.ts:78`) and has a dedicated branch for this route
  (`church-context.guard.ts:37-38`) that resolves `requestedChurchId` from
  `request.params.id` when the path starts with `/churches/`, then requires an
  `active` membership. There is no global route prefix, so that branch is live.
  Non-super-admins cannot reach another church. Super-admins can, by design.

- **`events.service.ts` `setAttendance` RSVP queries lack `churchId`** —
  rejected as a tenancy bug. The method calls `getOwnedEvent(churchId, eventId)`
  on its first line and throws if the event is not owned, so every downstream
  query keyed on `eventId` is transitively scoped. The narrower real issue
  (unvalidated `attendedMemberIds`) shipped in commit `cf43b78`.

- **`visitors.service.ts` `convertVisitorToMember` updates `visitorFollowups`
  by `visitorId` only** — rejected. The visitor is ownership-verified at line
  104, before that write.

- **Cent sums cast via `Number()` can overflow 2^53 in `offerings.service.ts`
  and `giving-goals.service.ts`** — rejected. That threshold is ~90 trillion
  cents. Not a real risk for this product.

- **`bg-linear-to-b` in `components/church/setup-church.tsx` is a typo for
  `bg-gradient-to-b`** — rejected. This repo is on Tailwind v4
  (`apps/web/package.json`), where `bg-linear-to-b` is the correct syntax.

- **Next.js server actions in `apps/web/actions/` accept `churchId` from the
  client without validating it against the session** — investigated during
  the wave (commit `c6b91bb`'s Part C), rejected as a real gap. Every action's
  target API route is behind `ChurchContextGuard` + `PermissionGuard`, and
  member-scoped routes (`/members/me`, `/offerings/me`, etc.) resolve identity
  server-side, not from the client-supplied `churchId`. Full per-action audit
  table is in that commit's worker report.

## Post-wave follow-up (outside the wave, same day)

- `pnpm --filter api exec eslint` and `apps/web`/`packages/config` lint were
  all broken at baseline (fixed in `c2f0626`, `c9ea40b`). `apps/web` was
  crashing outright — `eslint-config-next@16`'s native flat-config exports
  fed through the legacy root `.eslintrc.cjs`, plus its `lint` script called
  `next lint`, which Next 16 removed entirely. Root `.eslintrc.cjs` deleted;
  `packages/config` got its own isolated config; `apps/web` got a proper flat
  `eslint.config.mjs`.
- Once lint actually ran on `apps/web` for the first time, it surfaced 13
  real pre-existing issues — all fixed in `459b466`, `6d665ec`, `d80a5b7`,
  `116522a`: unescaped JSX entities, two `setTimeout(async () => ...)`
  misused-promise bugs, a `Math.random()` purity violation in a memoized
  skeleton width, and three stale-closure bugs where a `useMemo`'s
  dependency array didn't cover the handlers its callback closed over.
